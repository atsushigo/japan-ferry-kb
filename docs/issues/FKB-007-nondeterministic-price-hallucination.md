# FKB-007：回答偶爾輸出知識庫沒有的價格數字（非確定性）

| Field | Value |
|---|---|
| Type / Priority / Status | Bug / High / Open |
| Component | chatbot-prompt、model |
| Found in | 提示詞 v2、gemini-3.5-flash-lite、知識文件 v3；預覽 1 次、chat-001 1 次、chat-002 1 次 |
| Reported | 2026-11-21 JST |
| Related | FKB-005、FKB-006 |

## Description
同一題「大阪到釜山船票多少錢？」重跑 3 次，第 2 次的回答出現：

> 陽台套房 BALCONY SUITE（2人）：**₩2/人**

知識庫的陽台套房票價是單程 ₩500,000／來回 ₩1,000,000（檢索回傳的票價段落有這一列），「₩2/人」不存在於任何來源。另外 2 次相同題目的價格全部正確。

## Recurrence（chat-001，2026-11-21，`evaluation/chat_runs/chat-001_2026-11-21/`，API、提示詞 v2、gemini-3.5-flash-lite）
A1 重複 3 次，第 1 次又出現知識庫沒有的價格：

> 陽台套房 BALCONY SUITE（2人）：₩2,500,000（檢索結果：₩500,000）

回答把自己列的錯誤金額和「檢索結果」的正確金額並排寫出，且該次輸出同時是拼接輸出（見 FKB-008）。`score_chat.py` 的數字溯源檢查正確抓到（憑空金額 `2500000`）。
預覽 3 次中 1 次、API 3 次中 1 次，兩種方法合計 2/6；兩者做法不同，不宜硬合併成一個機率，只能說「不是偶發的單一事件」。

## Recurrence 2（chat-002，重試已關閉，A1 重複 10 次）
A1 #7 再次出現：

> 陽台套房 BALCONY SUITE（2人）：₩2,500,000（註：檢索結果陽台套房單程為 ₩500,000）

**規律：三次錯誤全部發生在「陽台套房」這一列**（預覽「₩2/人」、chat-001「₩2,500,000」、chat-002「₩2,500,000」），其中兩次是同一個錯誤數字，並且都在同一行附註正確金額。API 兩輪合計 A1 為 2/13 次。
Suspected：輸出「（2人）：₩」時，前面的「2」帶偏下一個數字；陽台套房的人數是 2，但總統套房也是 2 人，卻沒有出錯，所以尚無法解釋，只是一個待驗證的線索。

## Steps to reproduce
在聊天流預覽反覆輸入「大阪到釜山船票多少錢？」；約每 3 次可能出現 1 次（樣本太小，真實頻率未知）。

## Expected / Actual
- Expected：所有金額逐字來自檢索結果。
- Actual：有一次輸出了不存在的金額。同一次回答還少列了來回價（單程以外），屬資訊不完整，不是錯誤。

## Root cause（Suspected，未驗證）
- 輕量模型在表格轉列表時發生生成錯誤；溫度不能調（Gemini 3 系列不開放），無法用降低隨機性緩解。
- 檢索結果（票價段落）本身是正確的，錯在生成階段。尚未用 Gemini 3.8 Flash 對照，所以不能斷言「換模型就好」。

## Resolution / Workaround（提案）
1. FKB-005：評測腳本加入「數字溯源檢查」（回答中每個金額必須出現在檢索到的段落中）與每題多次重複，用來量測發生頻率。
2. FKB-006：用同一批題目比較 Gemini 3.8 Flash。
2-1. ~~與 FKB-008 的失敗重試有關~~：chat-002 關閉重試後仍出現，無關。
2-2. 針對「陽台套房」這一列設計實驗：把人數放到價格後面（例如「單程 ₩500,000（2 人房）」），或改變票價表的欄位順序後重測，各 10 次以上。
3. 若頻率不可接受，可考慮把票價改成流程中的固定模板輸出（用程式節點直接引用檢索到的表格，不經模型改寫）。

## Verification
- 通過條件：每題各重複 ≥ 10 次，數字溯源檢查零違規；若無法達成，在 README 與報告中如實標示此限制。

## Lessons learned
- 單次預覽看起來全對不代表可靠；有非確定性的系統必須重複測量。
- 價格類錯誤應由規則式檢查擋下，而不是靠人讀。
