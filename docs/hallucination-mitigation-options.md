## 層級 1：改提示詞

**做什麼**：在系統提示詞加一條規則，限制模型輸出的格式與取數方式。不動知識庫。
**優點／缺點**：最快、可立即測；但是機率性，只能降低出錯率，不能保證為零。

**實例（本專案，提示詞 v3 的規則 10-1）**

```text
10-1. 列出票價時，每個艙等獨立一行，格式固定為：
艙等名稱：單程 ₩金額（客房人數：N 人）
金額必須逐字抄自檢索結果中「同一個艙等」那一列；人數只能寫在行尾括號內，不得放在金額前面。
```

- 為什麼這樣改：4 次錯價都在陽台套房那一列，其中 3 個錯誤值以「2」開頭，與該列人數「2 人」相同；所以把人數移到價格後面，並要求逐字抄同一列。
- 怎麼做：Dify 編排 → LLM 節點 → SYSTEM 欄貼上 → **發布更新**（API 跑的是已發布版本，不是草稿）。
- 結果（chat-004，A1 ×20，retry 關閉、已發布）：20/20 沒有金額不在檢索結果裡；六個艙等的價格與人數 20 次全部正確。改前 A1 約 4/33 次出錯，若錯誤率不變，20 次全對的機率約 8%，所以是支持證據，不是證明；還要再多跑幾輪確認。

## 層級 2：改知識文件的寫法

**做什麼**：不改事實，只改文件的表達，讓每個事實自成一句、價格與條件綁在同一行。表格的欄位對應對模型比較容易錯位。
**優點／缺點**：通常比提示詞更穩；但要重新上傳並重建索引，**召回測試必須重跑**（分段、分數都可能變）。

**實例（本專案）**

改前（現在的表格列）：

```text
| 陽台套房 BALCONY SUITE | ₩500,000 | ₩1,000,000 | 2 人 |
```

改後（每個艙等一句，數字與人數同一行）：

```text
- 陽台套房 BALCONY SUITE：單程 ₩500,000、來回 ₩1,000,000（每人；客房 2 人）。
```

操作步驟：
1. 先把現行檔案複製到 `knowledge/history/`（保留可追溯的舊版）。
2. 修改 `knowledge/osaka-busan-panstar.md` 的票價段，只改表達不改數字。
3. 在 Dify 知識庫更新該文件並等待重新索引。
4. 重跑召回測試（`run_recall.py --use-dataset-settings`，新 run 編號）確認票價段仍排第 1、分數沒有掉到閾值 0.71 以下。
5. 重跑 `run_chat.py` 的 A1 ×20，與改前比較。

## 層級 3：輸出後驗證（guardrail）

**做什麼**：LLM 回答後，用程式檢查回答裡每個金額是否出現在檢索到的段落，不符就不要送出，改回固定訊息（或重新生成）。
**優點／缺點**：**真正擋得住**，不靠模型自覺；但多一個節點，回答要整段檢查完才輸出，不能邊生成邊顯示。

**實例（本專案）**：`evaluation/score_chat.py` 已經在離線做同樣的檢查（`numeric_grounding`）。線上版是在 Dify 的 LLM 與回覆節點之間加一個「程式碼」節點，示意：

```python
import re

def main(answer: str, context: str) -> dict:
    amounts = re.findall(r"[₩¥￥]\s?[\d,]+", answer)
    bad = [a for a in amounts if a.replace(" ", "") not in context.replace(" ", "")]
    return {"ok": not bad, "bad": "、".join(bad)}
```

流程：開始 → 知識檢索 → 條件分支 → LLM → **程式碼（驗證）** → 條件分支（`ok` 為真 → 回覆；否則 → 固定訊息「這個數字無法確認，請查官方網站」）。
注意：以上只是示意，節點的輸入輸出寫法與沙箱限制要依 Dify 版本實測；規則與離線版一致（數字溯源），所以可以直接用 chat 測試驗證它有擋到。

## 層級 4：結構化資料＋查詢

**做什麼**：把票價放進資料表；模型只負責理解問題（例如「單程」「陽台套房」），由程式查表後直接輸出數字。數字完全不經過模型生成。
**優點／缺點**：數字**確定正確**，這是處理精確數字的標準做法；但要建資料表與 API，成本最高。

**實例（本專案，Phase 2 的 FastAPI＋PostgreSQL）**

```sql
CREATE TABLE fares (
  route TEXT, cabin TEXT, one_way_krw INT, round_trip_krw INT, occupancy INT,
  confirmed_on DATE, source_url TEXT
);
SELECT cabin, one_way_krw, occupancy FROM fares WHERE route = 'osaka-busan';
```

流程：LLM 判斷意圖與參數 → Dify「HTTP 請求」節點呼叫 FastAPI → 程式組好價格表 → 回覆。確認日期與來源也存在資料表，答案天然帶來源。

## 層級 5：換較強的模型

**做什麼**：改用能力更強的模型，例如 Gemini 3.8 Flash（目前用 3.5 Flash-Lite）。
**優點／缺點**：錯誤率可能下降；沒有保證，且有額度與費用。
**實例**：沿用同一組測試（A1 ×20），只改 LLM 節點的模型，比較錯價率、耗時、單次費用；見 [FKB-006](issues/FKB-006-llm-model-comparison-and-billing.md)。

## 另：Dify「標註回覆」

事先寫好人工確認過的問答，使用者問題夠相似時直接回傳，不經過 LLM。
- 適合：最常被問、答案固定的題目（例如票價表）。
- 缺點：價格更新後必須手動同步，否則會一直回舊答案；只有問題夠相似才命中；它繞過 LLM，會讓 RAG 本身的品質被掩蓋。若使用，測試要分開統計「命中標註」與「走 RAG」。

## 我們的選擇順序

1 → 3 → 4：先用提示詞（已測），再補輸出後驗證（有離線版可以直接搬），精確資料最後在 Phase 2 轉成結構化查詢。層級 2 在層級 1 不夠時再用；層級 5 看 FKB-006 的對照結果。
